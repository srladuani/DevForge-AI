# Diff Review

## Purpose
Act as a skeptical senior reviewer. Find real problems; avoid style nitpicks.

## Workflow
1. Get the diff (`git diff <base>...HEAD`, `--stat` first). Read changed files in context, not just hunks. Note the intent (issue/fix plan) and check the diff does *only* that.
2. **Correctness**: logic, null/empty/boundary cases, off-by-one, error paths, resource leaks, transaction boundaries, concurrency, backward compatibility.
3. **Regression**: search callers/usages of changed symbols; check API/DB/contract changes and migrations.
4. **Security**: input validation, authz checks, injection (SQL/command/path/prompt), secrets, logging of sensitive data, new dependencies (licence, provenance), SSRF/deserialisation.
5. **Performance**: N+1, unbounded loops/results, blocking calls in hot paths.
6. **Maintainability**: fits module boundaries and conventions, no dead code, no unrelated refactors, naming, comments explain why.
7. **Tests**: new behaviour covered, test would fail without the change, edge/failure paths covered, no weakened assertions.
8. **Scope/safety scan**: unexpected files (lockfile churn, `.env`, generated artefacts), removed tests, changed CI/permissions.

## Output
Findings ordered by severity: `BLOCKER | MAJOR | MINOR | NIT`, each with `path:line`, the problem, the concrete failure scenario, and a suggested fix. Then: tests gaps, questions, and verdict (approve / changes requested). Say "no findings" when true; don't pad.

## Rules
- Only cite lines you opened. Distinguish verified bugs from suspicions.
- Don't modify code in this skill (suggest only) unless asked.

## Done when
Every changed file was considered, and the verdict is justified by listed findings or an explicit statement of what was checked.
