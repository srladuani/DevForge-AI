# ADR-0016: Managed clones (clone-by-URL)
**Status:** Accepted (builds on ADR-0013; verified against a bare repository standing in for the Git host, not against github.com or bitbucket.org)
## Context
Until now a repository could only be added as a path to a checkout that someone had prepared on the machine running DevForge. That ties DevForge to one developer's machine and does not work for a shared server: other people's laptops (Windows, macOS) cannot supply a path, and the sandbox is Linux-only. A team deployment needs DevForge to obtain the code itself.
## Decision
1. **Add by URL.** A project member with manage rights gives a repository address (https, ssh or scp form on a configured Git host). DevForge clones it into a folder it owns (`devforge.repositories.managed-root`, default `~/.devforge/repos`), one clone per remote, shared by every project that uses it. The address is only accepted if a configured host adapter recognises it, so a credential is never sent to an arbitrary server; an address that contains a user name or token is refused.
2. **The requester's own credential, every time.** Cloning, proving access and refreshing use the requesting person's own verified Git connection that covers that repository (ADR-0013, scoped connections). The credential travels only in the environment of the one git process (`http.extraHeader`), never on a command line, in the clone's config, a log, an event or a message. There is no shared or service credential.
3. **Access is proved before anything is shared.** `git ls-remote` with the requester's credential must succeed before a clone is created or an existing one is reused. A second project adding the same URL therefore never gains access to a repository its member cannot read (R18).
4. **Fresh code for each run, from the branch the change goes into.** When a run starts, each managed repository is fetched with the starter's own connection and checked out at the repository's target branch (repository setting, else project setting, else the clone's current branch). If the starter has no usable connection or the host cannot be reached, the run continues on the code as last fetched and records a `REPOSITORY_NOT_REFRESHED` event saying so; an explicit Refresh fails loudly instead. The run pins the commit it started on, so later fetches do not change what it reads or cites.
5. **Paths can be switched off.** `devforge.repositories.allow-local-paths=false` (for a shared deployment) refuses registration by path; a path would let a project member point DevForge at anything the server can read.
6. Clones are DevForge's own: the working tree is reset to the remote branch on every refresh; local changes are never kept. Publishing is unchanged: it works from a history clone of the managed clone and pushes with the run owner's credential.
## Consequences
+ A shared Linux server needs no prepared checkouts and developers need nothing but a browser. + Access control follows the person's own Git permissions. − The agent sees what is on the remote branch, not unpushed local work. − Project membership is the access boundary for code read by runs: a member without their own Git access can still run on the last fetched code. − Clones are not yet removed when no project uses them (disk grows; add a sweeper). − Very large repositories clone slowly on first use (a 20 minute limit applies).
## Revisit when
Shallow or partial clones are needed for very large repositories; repositories need background refresh independent of runs; multi-tenant hosting.
