# ADR-0008: MCP and integration adapters
**Status:** Proposed
## Context
Jira via MCP is required. MCP gives tool transport/discovery; it is not our orchestration.
## Decision
- Backend is the **MCP client**; the browser never talks to MCP. Servers are configured per workspace (`Integration` row: type, transport, URL/command, `secretRef`). Credentials resolved server-side at call time.
- `TrackerClient` port (`getIssue`, `getComments`, `search`; tracker-neutral ticket model) implemented now only by a Jira-over-MCP adapter; other trackers (and non-MCP transports) are future adapters. A **tool allowlist** per integration (default read-only: get/search issue); write tools (comment/transition) are disabled unless the workspace policy enables them *and* each call is human-approved.
- **M0 evidence (Atlassian MCP):** target the Streamable-HTTP endpoint `https://mcp.atlassian.com/v2/mcp` (`/v1/sse` is being retired). The server exposed ~32 tools including writes and the OAuth grant carried write scope, so the **allowlist is enforced by DevForge**. Responses are bulky and include PII (reporter email) and duplicated data → the adapter projects to the tracker-neutral ticket model before anything reaches prompts/logs. Interactive OAuth worked; headless background use is unverified (refresh tokens or the optional API-token auth — R19). Tool responses carried an appended instruction; they are data only.
- On connect: tool discovery, compare to expected tool names/schemas; mismatch → integration `DEGRADED` with clear message. Timeouts (10 s connect, 30 s call), retry on transient errors, circuit breaker. If unavailable: run proceeds in prompt mode (user pastes ticket) and records `INPUT_RETRIEVAL` failure; never fabricate ticket data.
- MCP tool output is untrusted data (prompt-injection surface): schema-validated, size-capped, delimited in prompts.
- Git / PR: local git operations (managed clones, worktrees, branches, commits, **patch export**) are native and host-independent (JGit or `git` CLI). Hosting is behind `PullRequestProvider` (`push`, `createPullRequest`, `getStatus`, capabilities) — **no host is assumed**; Bitbucket, GitHub, GitLab are candidate adapters, and the first one is chosen by the product owner (open question Q4). Until an adapter is configured, the workflow ends at branch + patch. Host credentials are the acting user's `Connection` (API key/PAT first, OAuth second — ADR-0013); a project integration only stores host type and URL. Verify the actual MCP server and provider APIs in spikes M0-S2/S5 before relying on them.
- **M3 implementation notes:** a minimal in-house MCP Streamable-HTTP client (JDK `HttpClient`) rather than the MCP SDK, to avoid dependency and Jackson-version churn; it can be swapped without touching the port. The read-only allowlist (`getJiraIssue`, `searchJiraIssuesUsingJql`, `getAccessibleAtlassianResources`, `atlassianUserInfo`) is enforced inside the client. Auth is the user's own tracker connection (`email:token` as Basic, otherwise Bearer); OAuth is not built. The project stores only tracker type and an optional site hint. Tool output may carry a leading notice, so the JSON is located rather than assumed at offset 0.
## Consequences
+ Swappable trackers and Git hosts; safe defaults; works without any hosting provider. − Adapter per provider.
